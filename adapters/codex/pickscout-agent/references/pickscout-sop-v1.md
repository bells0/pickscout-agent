# PickScout 标准操作程序（SOP）v1

- 状态：accepted
- 版本：v1
- 日期：2026-08-13
- 适用对象：使用 PickScout 的用户、研究人员和仓库内 Agent

## 1. 使用方式

每次真实任务都按本 SOP 的固定外环运行。研究来源和工具顺序仍按信息价值动态调整。

执行时必须遵守 [方法论第 1.1 节：首要选品原则](pickscout-methodology-v1.md)。清单服务于当前商业决定，不把竞品细节变成硬门槛，不提前套用后续阶段要求，也不因非关键资料未齐而停止展示初步选项与有条件建议。

开始前先判断：

- 新任务：从步骤 0 开始。
- 恢复任务：先执行步骤 R，再回到对应阶段。
- 只读解释或状态汇报：读取现有产物后直接回答，不创建空任务目录。
- 开发仓库能力：遵循 `AGENTS.md` 的开发与验证要求，不套用真实候选模板。

### 1.1 统一市场研究方法与 Skill

本节只定义研究方法的接入，不替代 PickScout 的 A–G 阶段、证据与决定记录、模板或确定性计算。

1. 当前问题涉及品类全景、竞品、关键词、趋势、用户需求或参考款式时，在源项目读取 `skills/amazon-category-opportunity-research/SKILL.md`，并执行 [市场研究规范](market-research-v1.md)。项目 `.agents/skills/` 只链接此维护源。在其他工作区使用完整适配器时直接读随包镜像规范，不要求安装另一个 Skill。
2. 名称可见不足以代替读取。实际载入其 `SKILL.md` 后，再按当前问题选用研究模式、工具和口径；优先复用仍适用的报告与原始数据，仅补可能改变判断的缺口。卖家精灵可用时优先利用，缺少专门工具时继续使用现有来源。
3. 同一负责人在当前任务中使用该方法；经用户授权的多 Agent 分工复用同一范围和证据目录，不另建重复研究或独立事实库。新研究统一产出到 PickScout；历史外仓资料先保留原位置并引用，迁移时记录原件、目标与依赖。auto-amazon 负责 Listing、Seller Central、FBA、库存订单与运营执行，不另维护市场研究流程。
4. 用户只要求市场研究时，按 A 候选发现或 B 候选筛选支持其研究问题，不提前要求买样、完整供应成本或采购资料。需要后续阶段判断时回到本 SOP 的对应步骤；市场报告不代表样品、采购或履约已经通过。
5. 统一使用六维判断和带对象/阶段的 `advance / observe / reject / insufficient`。经济性缺完整成本写“未评估”，不把它当 A/B 的阻塞项；用户决定、授权和执行事实分别记录。
6. 发现链接失效时直接读取本仓维护源；安装的完整适配器使用随包规范。缺少专门数据工具时继续已有合法来源，注明覆盖限制，不把全局安装作为前提。

单一维护源：详细研究方法为本仓 `docs/market-research-v1.md`，研究 Skill 为根 `skills/amazon-category-opportunity-research/`；完整 Agent 适配器只镜像文档和模板，不形成第二套编辑源。决策 0014 取代 0013 的外仓维护归属；本机发现链接不进入公开包。

## 2. 角色分工

负责人对综合结论负责。复杂探索出现可独立研究的市场分支、证据/商业解释分歧或客户交付审读需求时，向用户提出最小协作分工及收益，由用户决定启动与范围；已有授权直接执行，普通任务不自动派发。角色分工与审读要求见[协作约定](selection-team.md)。

| 角色 | 负责 | 不自动负责 |
| --- | --- | --- |
| Agent | 理解目标、计划研究、取证、调用计算、解释和建议 | 最终经营决定、未经授权的外部动作 |
| 用户/决策者 | 确认目标、经营约束、授权和最终决定 | 填写完整研究表或手工整理全部证据 |
| 采购/运营人员 | 按冻结版本执行采购、包装、物流或上架动作 | 解释内部研究历史 |
| 确定性脚本 | 公式、校验、硬门槛和结构一致性 | 动态研究判断 |

## 3. 固定操作步骤

### 步骤 0：确认本轮要支持的决定

把要支持的动作及可接受投入/损失写清；未知时先给可选投入范围的依据，不虚构用户预算。依据[方法论第1.2节](pickscout-methodology-v1.md)匹配证据强度，形成明确倾向，不要求机会判断达到百分之百确定。

Agent 必须先用一句话写清：

> 本轮要帮助用户决定：`<是否继续研究 / 是否买样 / 是否量产 / 是否上架 / 发多少 / 选哪家物流 / 是否补货>`。

同时确认：

- 市场和履约方式；
- 当前阶段 A–G；
- 候选或任务范围；
- 用户已确认的经营条件；
- 需要单独授权的动作。

如果不同解释会改变研究对象、成本或外部影响，先请用户确认。其他情况下做合理假设并继续。

### 步骤 1：读取事实来源并恢复上下文

新任务至少读取：

1. `AGENTS.md`；
2. `docs/pickscout-methodology-v1.md`；
3. 本 SOP；
4. `docs/research-protocol-v0.md`；
5. 与当前阶段相关的决策记录。

已有任务另外读取：

1. `artifacts/research-progress.md`；
2. 当前任务最新 `decision-log.md`；
3. 最新 `research-brief.md`；
4. 最新报告、计算和用户决定；
5. 需要刷新或已过期的关键证据。

不得让模型记忆覆盖仓库事实。

恢复时以简报唯一的当前结论区确认建议、用户决定、有效交付与下一动作；旧版过程从决策日志/历史简报按需读取，不在简报顶部继续叠加“当前版本”。

### 步骤 2：初始化或更新任务包

真实研究需要时，在 `artifacts/<task-id>/` 创建或更新：

- `seller-profile.md`；
- `research-brief.md`；
- `evidence.jsonl`；
- `task-run-checklist.md`；
- 对应阶段所需的报告、计算或测试文件。

模板从 `templates/` 复制。不要为目录完整而创建暂时无用的空文件。

原始或敏感输入放入 `data/<task-id>/`；`artifacts/` 保存派生数据、任务过程和私有结果。

### 步骤 3：定义当前阶段门槛

从方法论的 A–G 阶段中选择一个当前阶段，并写清：

- 阶段输入；
- 阶段输出；
- 适用硬门槛；
- 最低证据包；
- 什么结果会 `advance / observe / reject / insufficient`；
- 哪些后续阶段门槛本轮明确不处理。

状态必须带对象和阶段，禁止只写孤立的 `advance`。

### 步骤 4：检查候选是否可比

多候选任务先填最低证据包矩阵：

| 候选 | 产品定义 | Amazon ASIN | 竞争 | 失败主题 | 供应（A/B非前提） | 合规/IP | 可比状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `<ID>` | `<有/缺>` | `<数量>` | `<有/缺>` | `<有/缺>` | `<有/缺>` | `<有/缺/不适用>` | `<comparable / discovery_only>` |

统计排名只使用同口径的 `comparable` 样本。商业推荐顺序可以综合直接参照、功能替代和专业推断，说明依据与差异；`discovery_only` 不自动禁止推荐先后，但不能据此宣称销量或成功率排名。矩阵中的非关键缺口不阻塞商业判断。

### 步骤 5：建立高价值未知项队列

每个未知项标记：

- `hard_gate`；
- `status_change`；
- `confidence_only`；
- `context_only`。

按以下顺序选择下一动作：决定性门槛 → 状态变化 → 关键假设 → 情景范围 → 背景补充。

每次行动前写清：

- 为什么现在查；
- 预计改变什么；
- 最低成本取得方式；
- 是否需要授权。

### 步骤 6：执行动态研究循环

重复以下循环，直到达到停止条件：

1. 取得当前最高价值证据；
2. 保存来源、时间、市场、口径、适用范围和独立性；
3. 更新 Claim、支持/反对关系和信息缺口；
4. 检查新证据是否改变阶段门槛或候选范围；
5. 必要时调整关键词、来源、工具和计划；
6. 向用户提供简洁进度，不输出冗长工具日志。

固定样本后再比较，不能在采集中途不断替换竞品以迎合结论。

A/B 按市场研究规范的八步履行分析义务，使用口径卡、来源/样本表、六维判断与九章 HTML 报告模板。样本范围有新证据需要改变时保留前后版本和理由，不把固定样本解释为禁止纠错。

### 步骤 7：执行阶段专用验证

根据当前阶段选择对应模块：

#### A 候选发现

- 从用户种子、问题或工作流生成候选；
- 覆盖多个功能家族，避免候选池只集中在易搜集的形态；
- 社交信号只用于发现；
- 输出候选池、排除项和下一项同口径研究计划。

#### B 候选筛选

- 为候选补齐最低可比证据包；
- 可从 5–10 个代表 ASIN 起步，按细分覆盖调整并记录理由，不设通用样本数门槛；
- 比较需求、竞争、用户任务、关键词、同规格评论/价格和具体进入限制；供应、样品和完整成本后置到相关阶段；
- 输出阶段建议，不输出采购授权。

#### C 样品筛选

- 供应来源默认使用 1688；
- 记录 offer ID、SKU、页面价、MOQ、材料、结构和可见重尺；
- 页面先查，缺失且会改变买样决定时才联系供应商；
- 联系文案须在发送前由用户确认；
- 把差评主题转成样品测试计划。

#### D 样品验证

- 按测试计划记录结果和照片/文件引用；
- 检查做工、气味、装配、稳定、耐久、破损和实际使用；
- 确定用户自己的销售包装；
- 实测净重、包装后长宽高和毛重；
- 明确通过、整改复测或淘汰。

#### E 采购与单位经济

- 取得目标数量的书面 RFQ、MOQ、交期和质检条件；
- 获取官方 FBA 费用和真实头程；
- 为每个输入记录来源和日期；
- 运行 `scripts/unit_economics.py`；
- 运行 `scripts/hard_gates.py`；
- 任一关键输入缺失时保持 `insufficient`。

#### F FBA 与首票物流

- 使用实测箱规，不使用旧估算订舱；
- 由 auto-amazon 对应执行负责人在授权下创建 FBA offer 和 Send to Amazon，回传实际 FC；PickScout 复用回执做物流决策支持；
- 对物流商发送同口径 RFQ；
- 比较门到仓全包总价、时效、最低消费、税费、IOR、保险和异常费；
- 木制品等特殊货物补齐如实申报和进口合规资料；
- 未授权前不创建不可逆费用、订舱或付款。

#### G 上线复盘

- 固定观察窗口；
- 回填销量、访问、转化、广告、退货、库存和贡献利润；
- 对比原三情景和关键假设；
- 决定补货、整改、观察或退出；
- 记录哪些证据真正改变了经营结果。

### 步骤 8：调用确定性工具并审计充分性

适用时运行：

```bash
python3 scripts/unit_economics.py <真实任务输入.json>
python3 scripts/hard_gates.py <真实任务输入.json>
```

随后按当前具体动作检查研究协议的充分性条件。真正阻断该动作的未解决缺口不能以 `criteria_satisfied` 停止；可管理的开放假设可带入限定试验，保留影响、投入边界和停止/调整条件，不要求所有可能改变后续结果的缺口清零。

### 步骤 9：形成阶段结论

对话先给结论，再给必要依据。固定结构：

```text
当前阶段：
Agent 建议：
为什么优先此方向、为什么现在值得：
建议投入到哪一步及试错边界：
适用条件：
最强支持证据：
最强反对证据：
关键未知：
用户需要决定什么：
下一项最低成本动作：
观察信号及停止/调整条件：
```

若涉及多个阶段，分别列出状态。例如“买样 `advance`；量产 `insufficient`；下单授权 `pending`”。

### 步骤 10：记录决定、执行授权动作并交接

发生决策检查点时：

1. 追加当前任务 `decision-log.md`；
2. 更新 `artifacts/research-progress.md`；
3. 用户明确决定时更新 `user-decision.md`；
4. 外部动作执行后记录执行事实；
5. 在对话中链接更新文件。

若任务暂停，保存停止原因、已完成项、开放缺口和恢复动作。若进入下一阶段，更新运行清单中的阶段和新门槛。

## 4. 恢复步骤 R

恢复任何中断任务时：

1. 读取总进度、任务决策日志、研究简报和最新报告；
2. 复述此前范围、已确认用户决定和当前阶段；
3. 检查证据是否过期、工具权限是否变化；
4. 区分“尚未授权”“已授权未执行”“已执行”；
5. 更新任务运行清单；
6. 从最高价值开放项继续。

不要因为聊天中出现过某动作，就推断它已经完成。

## 5. 外部动作审批表

| 动作 | 默认行为 |
| --- | --- |
| 公开资料搜索和只读仓库检查 | 可直接执行 |
| 登录账号内只读查看 | 需要用户提供或确认授权范围 |
| 付费数据、下载、导出 | 先确认成本与权限 |
| 联系供应商或物流商 | 完整文案/RFQ 先给用户确认 |
| 加购、下单、付款、订舱 | 每个动作单独明确授权 |
| 创建或修改 Amazon listing/货件 | 明确授权后执行 |
| 对外发布、公开站点或扩大访问 | 明确说明受众后授权 |

## 6. 文件和版本规则

- 原始/敏感输入：`data/<task-id>/`。
- 私有任务产物：`artifacts/<task-id>/`。
- 总进度：`artifacts/research-progress.md`。
- 可复用规则：`docs/`。
- 模板：`templates/`。
- 确定性工具：`scripts/`。
- 历史通过新版本和 `supersedes` 保留，不静默覆盖。
- 对外 PDF 只在内容冻结后生成，并检查字体、裁切、重叠和链接。

## 7. Git 与质量验证

研究私有产物保持 Git 忽略。稳定方法、协议、模板、脚本和测试完成后：

1. 检查只包含本任务相关改动；
2. 运行 `git diff --check`；
3. 按变更风险运行适用检查；镜像变更运行分发包契约测试，计算变更运行对应回归；完整回归命令为 `python3 -m unittest discover -s tests -v`；
4. 说明未验证部分；
5. 暂存、提交、推送和 PR 交给本仓当前绑定的交付负责人。无该角色时交付文件与验证记录并报告缺口，不自行新建角色或代交付；合并单独授权。

## 8. 一页执行检查

开始前：

- [ ] 当前决定和阶段明确。
- [ ] 已读取方法论、SOP、研究协议和当前任务事实来源。
- [ ] 已区分已确认条件与假设。
- [ ] 已建立或更新任务运行清单。

研究中：

- [ ] 统计排名使用同口径数据；商业推荐顺序有明确依据和取舍，两者未混写。
- [ ] 当前动作能改变门槛、状态或关键假设。
- [ ] 证据来源、时间、口径和独立性已记录。
- [ ] 支持、反对和缺口同时保留。
- [ ] 未经授权没有外部影响动作。

交付前：

- [ ] 状态带对象和阶段。
- [ ] 事实、推断、假设、建议和用户决定分开。
- [ ] 计算使用真实、有来源的输入。
- [ ] 决策日志和总进度已同步。
- [ ] 下一动作低成本、可逆且明确。
- [ ] 执行交付物对无上下文读者没有歧义。
