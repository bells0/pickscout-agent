# PickScout 研究协议 v0

> 本协议规定证据义务、充分性、建议和停止条件。固定的人员/Agent 操作外环见 [PickScout 标准操作程序 v1](pickscout-sop-v1.md)，方法论与阶段门槛见 [PickScout 方法论 v1](pickscout-methodology-v1.md)。SOP 不固定搜索来源和工具顺序。

## 1. 目的与适用范围

本协议用于在当前仓库的 Codex 对话中开展 Amazon US FBA 选品前研究。它规定 Agent 必须维护的状态、证据义务、决策点和停止条件，不规定固定的搜索步骤、来源顺序或工具编排。

每项 P0 研究必须从至少一个具体种子开始：关键词、需求描述、明确细分类目、ASIN、URL 或候选清单。零种子的全市场扫描不属于本协议范围。

研究遵循以下边界：

- Agent 负责规划、取证、解释、复算调用和建议；用户负责最终经营决定。
- 公开且可逆的低成本研究可以直接进行。付费数据、账号授权或具有外部影响的动作必须先获得用户确认。
- 模型记忆和模型总结不能充当实时市场证据。
- 不绕过登录、验证码、访问控制或平台限制；不可访问的关键数据作为信息缺口处理。

## 2. 任务产物与标识

真实任务的私有产物保存在 `artifacts/<task-id>/`；原始或敏感输入保存在被 Git 忽略的 `data/`。任务至少应能恢复以下内容：

| 产物 | 建议文件 | 恢复用途 |
| --- | --- | --- |
| 卖家画像快照 | `seller-profile.md` | 还原当时使用的经营约束和版本 |
| 研究简报 | `research-brief.md` | 还原种子、范围、预算、当前计划、状态和缺口 |
| 证据账本 | `evidence.jsonl` | 保存逐条、可追溯的证据记录 |
| 单位经济输入与输出 | `unit-economics-input.json`、`unit-economics-output.json` | 独立复算三种情景与输入新鲜度 |
| 供应硬门槛输入与输出 | `hard-gates-input.json`、`hard-gates-output.json` | 独立复算 MOQ、交期与初始现金占用 |
| 阶段性或待审阅报告 | `research-report-v<version>.md` | 保存当时的分析和 Agent 建议 |
| 用户决定 | `user-decision.md` | 保存用户独立作出的决定 |
| 决策检查点日志 | `decision-log.md` | 按时间保存会改变后续行动的建议、用户决定和进度变化 |

`task_id`、`candidate_id`、`claim_id`、`evidence_id` 和信息缺口 ID 在任务内保持稳定。修订记录通过递增版本和 `supersedes` 关系完成，不覆盖会影响历史判断的旧版本。

跨任务总进度统一维护在 `artifacts/research-progress.md`。它只汇总当前漏斗、任务状态、明确用户决定、待决定事项和相关文件，不替代各任务的证据账本、报告或决策日志。

### 2.1 决策检查点

以下任一事件发生时，Agent 必须在本轮工作结束前更新当前任务的 `decision-log.md` 和跨任务总进度：

- 类目或研究范围改变；
- 候选入围、降级、淘汰或优先级改变；
- Agent 建议状态改变；
- 用户明确选择继续、观察、放弃或暂不决定；
- 用户授权或暂停询价、发样、采购等外部动作；
- 新证据使原有判断失效、部分适用或被替代；
- 研究进入暂停、恢复、待输入、样品验证或复盘阶段。

每条检查点使用稳定 `checkpoint_id`，至少记录时间、范围、触发原因、选项、Agent 建议、用户决定、理由、依据文件、关键未知、下一动作、复盘条件和 `supersedes`。Agent 建议和用户决定必须分开；用户没有明确表态时记录 `pending`，不得由 Agent 推断。

`decision-log.md` 是任务时间线；`user-decision.md` 是用户对某个候选或经营动作的明确决定快照。后者仅在用户明确表达决定后创建或更新。模板见 `templates/decision-log.md` 和 `templates/user-decision.md`。

## 3. 建立和更新研究任务

Agent 应先从对话中提取已有信息，只补问会显著改变范围、硬门槛、研究成本或建议状态的缺口，不要求用户先填写完整表单。

进入 `researching` 前，至少完成：

- 确认一个具体种子，并为任务和候选分配稳定 ID；
- 写明核心问题、市场、候选边界、允许的扩展范围和明确排除项；
- 保存所用卖家画像的版本化快照，区分已确认约束和未确认假设；
- 写明允许使用的来源、已有权限，以及需要额外授权的动作；
- 记录时间预算和数据成本预算；
- 列出适用硬门槛、必填分析维度、初始信息缺口和停止条件；
- 在对话中简要复述目标、关键假设、当前计划和预计限制。

范围存在重大歧义且不同解释会改变研究对象或产生额外成本时，任务保持 `draft` 并请求用户确认。信息足够、动作可逆时，不为遵循模板而强制暂停。

任务状态只用于恢复进度，不代表固定执行顺序：

| 状态 | 含义 |
| --- | --- |
| `draft` | 种子或关键范围仍待确认 |
| `researching` | 正在动态取证、分析或更新计划 |
| `needs_input` | 可由用户补充高影响输入后继续 |
| `blocked` | 关键来源、权限或能力不可用，当前无法继续 |
| `ready_for_review` | 仅在停止原因为 `criteria_satisfied` 时使用 |
| `decided` | 用户已明确作出并记录决定 |
| `archived` | 任务不再活跃，历史产物仍保留 |

## 4. 动态研究与信息价值

每次选择下一项动作时，Agent 应比较当前未解决问题的预期决策价值，而不是按预设清单机械执行。优先处理满足以下任一条件的信息：

- 可能使硬门槛变为通过或不通过；
- 可能改变 `advance`、`observe`、`reject` 或 `insufficient`；
- 能验证或推翻建议所依赖的重要假设；
- 能显著缩小悲观、基准和乐观情景的不确定范围；
- 能直接确定下一项低成本验证动作。

排序时同时考虑决策影响、当前不确定性、来源质量、取得成本、时效和可逆性。不需要伪造精确的信息价值分数；应在研究简报中记录“为什么现在查它”以及预期改变什么。

新证据到达后，Agent 应重新判断：

1. 它是否改变硬门槛、Claim、缺口或候选范围；
2. 当前最高价值问题是否变化；
3. 是否应补查独立来源、请求用户输入、调用确定性脚本、跳过低价值维度或提前停止；
4. 当前计划、覆盖状态和对话进度是否需要更新。

来源选择应匹配结论风险。官方、监管、用户授权或有许可的一手数据优先；社区和个人经验可用于发现线索或消费者语言，但不能单独支持高风险经营结论。

## 5. Claim、证据和信息缺口

### 5.1 Claim 管理

所有会影响建议的陈述应有稳定 `claim_id`，并标记为：

- `fact`：来源直接支持、无需额外推演；
- `inference`：由已列证据和明确规则得出；
- `hypothesis`：尚未得到充分支持、需要验证。

Claim 应写明分析维度、市场、时间和适用范围，并分别关联支持与反对的 `evidence_id`。推断必须展示推演依据；假设不得在报告中伪装成事实。

### 5.2 证据记录

每条用于支持、反对或限定关键 Claim 的信息都应按 `templates/evidence-record.schema.json` 单独记录。至少做到：

- 保存任务、候选、Claim、信号类型和决策影响；
- 保存发布者、URL 或仓库内文件引用、发布时间、采集时间和使用限制；
- 保存市场、观察窗口、指标口径、单位、样本或适用范围；
- 保存可核对的原始摘录或观测、内容哈希、提取方法及工具或模型版本；
- 对相关性、权威性、新鲜度、直接性、完整性、一致性和可操作性给出高 / 中 / 低及文字原因；
- 标记证据是支持、反对还是中性；
- 保存来源家族、上游来源和独立性判断。

无法确认上游独立性时，按“不独立”处理。多个页面若复用同一数据服务、报告或上游资料，不得计为多个独立来源家族。内容重复可以关联同一 Claim，但不能用引用数量抬高覆盖度。

过期证据保留在账本中并标记，不参与关键计算。无法回溯的内容不能作为最终报告中的事实。发生来源冲突时，不静默平均或删除任一方；应建立冲突组，说明口径差异、当前处理状态和对建议的影响。更正证据时新增版本，并将旧记录标为已被取代或失效。

### 5.3 信息缺口

每个未回答问题都应记录所属任务、候选、分析维度、信号类型、可取得性、阻塞原因、建议取得方式、预计成本、优先级、状态和版本。`decision_impact` 必须是：

- `hard_gate`：可能改变硬门槛状态；
- `status_change`：可能改变 Agent 建议状态；
- `confidence_only`：只影响置信度说明；
- `context_only`：只补充背景。

存在未解决的 `hard_gate` 或 `status_change` 缺口时，不能以 `criteria_satisfied` 停止。

## 6. 分析、硬门槛和确定性计算

Agent 根据候选实际情况选择研究路径，但必须覆盖或明确标缺以下维度：

1. 需求与趋势；
2. 竞争与进入壁垒；
3. 消费者问题与差异化空间；
4. 单位经济与现金占用；
5. 供应链与履约风险；
6. 合规与知识产权风险；
7. 证据完整度与不确定性。

适用硬门槛至少包括平台销售资格和品类限制、产品安全与认证、知识产权、FBA 履约限制、悲观情景单位贡献利润、MOQ / 交期 / 最大现金占用，以及用户明确禁区。每项硬门槛记录 `pass`、`fail` 或 `unknown`、判定依据和证据 ID。

一般情况下，任一硬门槛为 `fail` 时建议必须为 `reject`，任一硬门槛为 `unknown` 时建议必须为 `insufficient`。提前放弃例外见第 7 节。

费用、利润、阈值和情景结果应交给仓库内确定性工具。Agent 不猜测售价、尺寸、重量、成本或费用。单位经济必须：

- 为每项输入记录数值、币种、市场、时间和来源；
- 以任务研究截点和逐字段新鲜度阈值验证每项输入，拒绝未来或过期数值；
- 完成悲观、基准和乐观三种情景；
- 保存公式版本、输入、输出、缺失值和明确假设；
- 将过期数据和无来源数值排除在关键计算之外。

使用 `scripts/unit_economics.py` 计算单位经济，使用 `scripts/hard_gates.py` 判断 MOQ、交期和初始现金占用。供应硬门槛缺少真实输入时必须返回 `unknown`，并使 Agent 建议保持 `insufficient`；不得用示例值、行业均值或模型猜测代填。

## 7. 信息充分性与停止

只有同时满足以下条件，停止原因才可设为 `criteria_satisfied`，任务才可进入 `ready_for_review`：

1. 每个必填分析维度至少有一项可信证据，或明确记录缺口；
2. 所有适用硬门槛均为 `pass` 或 `fail`，不存在 `unknown`；
3. 需求和竞争判断各覆盖至少两种不同信号类型，并分别来自至少两个相互独立的来源家族；只有一个来源家族时不得建议 `advance`；
4. 单位经济全部必填输入有来源，且三种情景已由确定性工具完成；
5. 关键数据满足新鲜度要求，过期数据未参与关键计算；
6. 来源冲突已解释、保留或升级给用户；
7. 建议依赖的假设全部显式列出；
8. 不存在未解决的 `hard_gate` 或 `status_change` 信息缺口；
9. 报告包含支持证据、反对证据、最强反对理由、置信度原因和下一步动作。

提前放弃是上述充分性条件的唯一例外：若一个具有否决作用的硬门槛 `fail` 已由官方、用户授权或用户确认的证据验证，Agent 可以给出 `reject` 并使用 `criteria_satisfied`，无需继续搜集不会改变放弃决定的信息。尚未评估的其他硬门槛仍标为 `unknown`，并说明为什么它们不可能推翻这次 `reject`；所有未继续的分析维度必须逐项标记 `skipped_due_to_decisive_hard_gate`，并引用该否决门槛，不能伪装成已覆盖。

其他停止原因不会自动进入 `ready_for_review`：

| 停止原因 | 状态与产物 |
| --- | --- |
| `budget_exhausted` | 保持可恢复状态，输出信息不足的阶段性报告和最高价值下一项信息 |
| `source_unavailable` | 根据是否可由用户补充转为 `needs_input` 或 `blocked` |
| `user_stopped` | 保留当前状态、计划和全部产物，等待用户继续 |

达到时间或数据成本上限不等于信息充分。

## 8. Agent 建议

每个阶段性或待审阅报告只能使用以下建议状态：

- `advance`：硬门槛通过，核心证据达到要求，下一项验证有行动价值；
- `observe`：没有明确放弃理由，但当前行动价值不足，适合等待或监测；
- `reject`：硬门槛失败或证据明显不利；
- `insufficient`：高影响证据或关键计算缺失，暂不能形成经营建议。

建议必须写明适用条件、最强支持证据、最强反对证据、关键未知、三情景结果、置信度及原因和下一步低成本验证动作。置信度使用高 / 中 / 低和文字原因，不表示成功概率。

Agent 建议不能自动成为用户决定。仅当用户明确表达决定后，才按 `templates/user-decision.md` 记录 `continue`、`observe`、`drop` 或 `undecided`。

## 9. 暂停、恢复、范围变化与版本

暂停前，Agent 应更新研究简报中的任务状态、停止原因、当前计划、已覆盖维度、开放缺口、最近产物版本和下一恢复动作。工具失败也应先保留已取得证据和计算输入。

恢复时，Agent 不依赖聊天记忆猜测，而应：

1. 读取卖家画像快照、最新研究简报、证据账本、计算结果、报告和用户决定；
2. 核对任务、候选和版本关系，并检查关键来源是否因时间变化而需要刷新；
3. 在对话中概述此前范围、完成项、未完成项、当前建议和下一最高价值动作；
4. 清除已结束的临时停止原因，并从适当状态继续。

用户改变范围或经营约束时，应递增研究简报或画像版本，标记哪些旧证据、Claim、计算和建议仍适用、仅部分适用或已失效。旧版本保留用于审计，不静默混用。

用户补充报价、样品或真实经营数据后，应新增证据与计算版本，并在新报告中说明“什么变化、为什么改变或没有改变建议”。

凡上述变化构成第 2.1 节的决策检查点，还必须同步更新任务 `decision-log.md` 和 `artifacts/research-progress.md`；只有报告版本变化、没有决策影响的编辑不单独制造检查点。

## 10. 完成检查

提交阶段性或待审阅报告前，Agent 至少确认：

- 报告中的关键事实都能回溯到证据 ID 和来源；
- 事实、推断、假设和建议没有混写；
- 硬门槛状态、信息缺口和停止原因一致；
- 计算结果来自已保存、可复算且有来源的输入；
- `ready_for_review` 仅对应 `criteria_satisfied`；
- Agent 建议和用户决定保存在不同产物中；
- 敏感输入、凭据和商业机密没有进入版本控制。
