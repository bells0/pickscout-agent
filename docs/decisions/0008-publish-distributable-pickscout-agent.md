# 0008：发布可分发的 PickScout Research Skill

- 状态：accepted
- 日期：2026-08-18
- 部分取代：0002 的决策 5 与“仓库内再创建 Skill 子包”备选结论；0007 的决策 7 与“创建 PickScout Skill”备选结论

## 背景

0002 和 0007 在产品验证期拒绝 Skill 子包，是为了避免方法尚未稳定时形成第二套产品边界。此后，PickScout 已将固定外层决策循环、A–G 阶段、最低证据包、证据与决定分离、恢复流程、模板和确定性脚本沉淀为可运行的方法论与 SOP。

用户现明确要求把这套工作流固化为 Skill，分发给其他用户并开源。继续只依赖根目录 `AGENTS.md` 会把使用者限制在本仓库，也无法形成标准安装单元。

## 决策

1. 在 `skills/pickscout-research/` 维护可安装、自包含的 Skill 发布包，不使用已经否决的 `.agents/skills/` 隐式项目注入路径。
2. 根目录 `AGENTS.md` 继续定义 PickScout 源仓库的开发、真实研究和隐私边界；Skill 是面向其他工作区和用户的分发形态，不替代源仓库契约。
3. Skill 的 `SKILL.md` 提供便携运行入口，详细方法、SOP 和研究协议放入 `references/`，任务模板放入 `assets/templates/`，确定性计算放入 `scripts/`。
4. Skill 必须能够脱离本仓库运行；它不得要求用户安装插件、MCP 或修改项目配置，除非具体任务另行明确授权。
5. 根仓库中的方法论、协议、模板和确定性脚本仍是研发事实来源。发布包中的镜像文件必须通过契约测试与源文件保持一致。
6. 公开发布前必须明确选择开源许可证、检查敏感信息与第三方内容、确认仓库受众和可见性，并完成一次从干净目录安装的验收。
7. 创建和验证发布包不等于授权公开仓库、发布 Release、修改仓库可见性或安装到用户级目录；这些外部动作分别取得确认。

## 为什么现在改变

- 过去的风险是方法不稳定导致过早抽象；当前已有方法论、SOP、协议、模板、脚本和真实工作经验作为稳定输入。
- 当前新增的风险是源仓库与分发包发生漂移；对镜像文件做内容一致性测试是能够直接发现该风险的最低成本控制。
- Skill 只封装已验证的专业流程，不引入第二套运行时、页面向导、数据库或 MCP。

## 影响

- 其他 Codex 用户可以安装 `pickscout-research`，在自己的工作区使用同一方法。
- 源仓库仍可继续做产品验证与方法迭代。
- 修改镜像范围内的模板或脚本时，必须同步更新 Skill 包；测试会在遗漏时失败。
- 仓库在许可证与可见性确认前仍是“开源发布候选”，不能仅因包含 Skill 文件就宣称已经完成开源发布。

## 验证

1. 使用 Skill 标准校验器检查名称、frontmatter 和目录结构。
2. 运行发布包契约测试，确认镜像文件一致、引用资源存在且无模板 TODO。
3. 运行现有完整回归，确认打包没有改变计算行为。
4. 公开前从干净目录安装，并用至少一个真实、有种子的研究请求做前向验收。
