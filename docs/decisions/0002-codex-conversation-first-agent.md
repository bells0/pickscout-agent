# 0002：基于 Codex 的仓库级对话 Agent

- 状态：accepted
- 日期：2026-07-30
- 后续：关于不创建 Skill 发布包的部分已由 [0008](0008-publish-distributable-pickscout-skill.md) 取代；仓库级运行与隔离原则继续有效。

## 背景

PickScout 的核心价值不是提供一套固定页面，而是让个人卖家能够像与专业研究员协作一样，通过对话逐步表达目标、补充条件、检查证据、改变方向并作出决定。

当前 Git 仓库将长期用于开发、调试和稳定 PickScout。它不是一个安装其他 Skill 的容器，而是 PickScout Agent 自身的完整工作台：

- 用户希望整个研究过程中始终有 Agent 介入；
- 不同候选的信息路径差异很大，不适合写死步骤；
- 当前使用场景可以直接基于 Codex，不需要重新实现通用 Agent；
- 所有专业规则、脚本和研究产物都应限制在当前仓库，不能影响其他项目；
- 结构化证据和计算仍然重要，但应成为 Agent 的工作产物与工具，而不是独立产品界面的前提。

## 决策

1. PickScout v0 直接运行在当前 Git 仓库的 Codex 任务中，对话是主要交互方式。
2. Codex 提供 Agent 运行时，包括对话、推理、任务连续性、工具选择、权限和执行。
3. 仓库根目录 `AGENTS.md` 定义 PickScout 的身份、工作边界、专业原则、研究要求和安全约束。Codex 从本仓库工作时自动读取这些规则。
4. 详细的 Amazon FBA 方法、来源规则、证据规范、模板和计算脚本全部保存在当前仓库，并由根目录 `AGENTS.md` 按需引用。
5. 不创建 `.agents/skills/pickscout-research/`，不安装用户级 Skill 或插件，不修改仓库外的 Codex 配置。
6. Agent 根据当前目标、证据和用户反馈动态决定研究顺序与工具调用，不开发固定步骤的页面向导或顶层工作流引擎。
7. 关键状态必须跨轮次持久保存为当前仓库内的私有研究产物，不能只依赖聊天上下文。
8. 搜索、浏览、文件处理和协作优先复用 Codex 已有工具。
9. 只有高价值授权数据无法通过现有工具取得时，才在用户确认后使用仓库级 `.codex/config.toml` 增加 MCP。项目配置只服务于本仓库。
10. v0 不通过 Codex SDK 嵌入自建应用；是否需要独立产品界面留待仓库级 Agent 工作流验证后决定。

## 仓库边界

```text
pickscout-agent/
├── AGENTS.md                 # 始终生效的 PickScout Agent 契约
├── docs/                     # PRD、决策和专业研究协议
├── templates/                # 后续沉淀卖家画像、证据和报告模板
├── scripts/                  # 后续沉淀确定性计算与校验
├── data/                     # Git 忽略的原始或敏感输入
└── artifacts/                # Git 忽略的研究任务和调试产物
```

目录按实际验证结果逐步创建，不为完整结构而提前生成空文件夹。

`.codex/config.toml` 不属于预设结构。只有确有项目级 MCP 需求且用户明确同意时才创建。

## 职责边界

| 交给 Agent 动态判断 | 交给仓库内确定性工具或规则 |
| --- | --- |
| 如何理解用户目标和当前上下文 | 单位经济与费用公式 |
| 下一步最有价值的信息是什么 | 必填字段和数据类型校验 |
| 选择哪些允许访问的来源和工具 | 引用是否存在且可回溯 |
| 是否调整关键词、范围或研究计划 | 硬门槛的确定性条件 |
| 如何解释冲突证据与不确定性 | 用户授权与外部影响动作的审批边界 |
| 如何在对话中组织建议和追问 | 研究产物的结构和版本要求 |

原则是“Agent 驱动、仓库约束”：不把专业判断写成僵化流程，也不让 Agent 猜测本应确定计算或验证的内容。

## 备选方案

### 仓库内再创建 Skill 子包

不采用。当前仓库本身就是完整工作台，增加 `.agents/skills/pickscout-research/` 会形成不必要的第二层产品边界。

### 安装用户级 Skill 或插件

不采用。用户级安装会把未稳定的 PickScout 行为带到其他项目，不符合隔离调试要求。

### 自建对话应用和 Agent 编排

暂不采用。它会把早期投入转向通用运行时、会话、权限、工具调度和前端，而不是验证选品研究能力。

### 直接 fork LobeHub

暂不采用。LobeHub 可以继续作为交互参考，但 v0 已有 Codex 作为对话和工具运行环境，直接 fork 会重复建设通用 Agent 平台。

### 完全无结构的聊天提示词

不采用。仅靠聊天上下文无法稳定维护证据、公式、版本和用户决定，也不利于跨轮次恢复与复盘。

## 影响

- v0 的首个可运行产物是当前仓库根目录的 `AGENTS.md`，而不是 Skill 或 Web 应用。
- 原“研究工作台、证据面板、决策报告”改为由 Agent 管理并在对话中按需展示的仓库内研究产物。
- 产品验收必须覆盖自然语言启动、计划调整、追问、打断恢复和跨轮次持久化。
- 技术实现优先级变为：`AGENTS.md` → 仓库文档与模板 → 确定性脚本 → 必要的项目级 MCP。
- 10 个候选的阶段 A 试点可以立即在本仓库的 Codex 对话中开展，不等待独立应用开发。
