# 0001：Amazon US FBA 与证据优先的决策辅助

- 状态：accepted
- 日期：2026-07-30

## 背景

PickScout Agent 面向刚开始跨境电商的个人卖家。初期设想同时覆盖 Amazon 与 Temu，并参考通用 Agent 平台构建产品。

前期调研表明，个人卖家需要的不是一个无领域能力的通用聊天机器人或单一“机会分数”，而是：

- 主动搜集足以支持选品决策的信息；
- 区分有用证据、噪声和未知项；
- 将市场信号与个人资金、供应链、履约和风险条件结合；
- 由 Agent 提供可解释建议，再由用户作出最终决定。

同时，多平台数据结构、履约方式和经营约束差异较大。过早同时覆盖 Amazon 与 Temu 会削弱验证质量。

## 决策

1. v0 聚焦 Amazon US FBA 的选品前研究。
2. 产品采用 evidence-first 的人机协作模式：
   - Agent 负责搜集、整理、测算、解释和提示；
   - 用户负责采购、上架和其他关键经营决策。
3. 产品采用对话优先的专业 Agent 形态；证据、计算和决策报告作为 Agent 维护的持久化研究产物，而不是独立界面的前提。具体运行形态见 [0002](0002-codex-conversation-first-agent.md)。
4. 关键事实必须可追溯；事实、推断、假设和建议必须分离。
5. 数据接入优先使用用户输入、授权 API 和有许可的数据服务，不以绕过访问控制的网页抓取作为核心能力。
6. Temu 在 Amazon 研究闭环验证后，作为独立平台模型评估，不直接复用 Amazon 评分。
7. LobeHub 仅作为 Agent 交互与任务组织参考，不作为 v0 业务底座或直接 fork 目标。

## 备选方案

### 同时覆盖 Amazon 与 Temu

暂不采用。两个平台的数据、定价、履约和卖家模式不同，会让 v0 难以定义统一且可信的判断标准。

### 先做无结构的通用选品聊天机器人

不采用。对话是主要交互，但必须由当前仓库的专业规则、确定性工具和持久化研究产物支撑，不能只依赖临时聊天上下文。

### 直接 fork LobeHub

不采用。LobeHub 解决的是通用 Agent、模型和插件平台问题，不能替代 PickScout 的证据、经营约束和确定性计算模型；同时会引入较高的许可和维护成本。

### 先做大规模 Amazon 数据抓取

不采用。平台政策、数据许可和访问稳定性风险过高，也会让产品价值依赖难以控制的数据基础。

## 影响

- v0 的首要工作是验证研究与决策流程，而不是连接最多的数据源。
- P0 从用户提供的关键词、需求描述、明确细分类目、ASIN、URL 或候选清单开始，在限定范围内主动研究；宽泛主题发现和零种子的全市场扫描延后。
- 需要建立证据、来源、口径、冲突和新鲜度的数据模型。
- 需要定义“信息足够”的停止条件和信息不足时的降级行为。
- 利润和评分必须能确定性复算。
- 试点应使用 10 个真实 Amazon US FBA 候选。
- Temu、自动监测、多用户和店铺运营能力不进入 v0。
- v0 复用 Codex 作为 Agent 运行时，不开发独立聊天应用和通用 Agent 编排。

## 后续动作

1. 按 [v0 产品需求文档](../product-requirements-v0.md) 完成 Codex 对话式研究模板。
2. 选择 10 个真实候选开展阶段 A 验证。
3. 确认经营模式、资金范围、账号权限和现有数据来源。
4. 人工验证完成后再制定 v0 实现计划。
