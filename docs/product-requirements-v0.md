# PickScout Agent v0 产品需求文档

- 状态：Draft
- 版本：v0
- 日期：2026-07-30
- 首发用户：初步进入跨境电商的个人卖家
- 首发场景：Amazon US / FBA / 选品前研究与决策支持

## 1. 产品摘要

PickScout Agent 是一个运行在 Codex 中、以对话为主要交互方式的专业化商机探测与选品研究 Agent。

v0 不重新开发通用 Agent 运行时、聊天前端或固定流程系统。Codex 提供对话、推理、任务连续性和工具调用能力；当前 Git 仓库通过根目录 `AGENTS.md`、领域文档、模板、确定性脚本和研究档案定义 PickScout 的专业行为。用户通过持续对话提出目标、补充信息、追问和调整方向，Agent 动态规划并执行研究，最后给出可解释的建议、风险和下一步验证动作，由用户作出最终决定。

核心闭环：

```text
用户与 PickScout 对话
  → Agent 理解经营约束和研究目标
  → Agent 动态制定并调整研究计划
  → Agent 调用搜索、浏览、文件和数据工具
  → Agent 维护证据、缺口和研究档案
  → Agent 调用确定性计算与校验工具
  → Agent 在对话中给出带证据的建议
  → 用户追问、修正或作出决定
  → Agent 保存决定与后续结果
```

## 2. 已确定的产品方向

1. v0 面向个人卖家，而不是品牌团队、供应链团队或服务商。
2. 首发聚焦 Amazon US FBA；Temu 仅保留未来扩展边界。
3. 分析单位优先采用“客户需求 / 关键词簇 / 细分市场 + 代表 ASIN”，而不是宽泛大类目。
4. 对话是产品主体。用户在一个持续的 Codex 任务中提出目标、追问、打断、修正和决策。
5. 研究顺序、工具选择和补充问题由 Agent 根据当前证据动态规划，不采用写死的页面向导或固定步骤编排。
6. 研究简报、卖家画像、证据账本、计算结果和决策记录作为对话背后的持久化工作产物，由 Agent 维护并按需在对话中展示或链接。
7. Codex 作为 Agent 运行时；当前 Git 仓库本身就是 PickScout 的运行和调试工作台，以根目录 `AGENTS.md`、参考资料、模板和确定性脚本实现专业能力。
8. Agent 负责搜集、去重、归纳、解释、调用工具和提示；用户保留最终经营决策权。
9. 事实、推断、假设和建议必须明确区分。
10. 利润、费用、阈值和证据完整性校验采用确定性工具；Agent 不猜测缺失数值。
11. Amazon 数据接入优先采用授权 API、用户导入和有许可的数据服务，不以隐蔽网页抓取作为核心能力。

对应产品决策见 [0001-amazon-us-fba-evidence-first.md](decisions/0001-amazon-us-fba-evidence-first.md) 和 [0002-codex-conversation-first-agent.md](decisions/0002-codex-conversation-first-agent.md)。

## 3. 背景与问题

个人卖家的选品信息分散在平台工具、第三方数据、消费者反馈、供应商报价、物流费用和合规资料中。常见问题包括：

- 搜集到的信息很多，但不知道哪些会真正改变决策。
- 不同来源的时间、口径和可信度不一致。
- “搜索热度高”容易被误判成“适合自己经营”。
- 利润估算遗漏广告、退货、仓储、入仓、损耗或现金周期。
- 推荐结果只有分数，没有证据、反例和不确定性。
- 一次研究结束后，判断依据和真实经营结果没有形成反馈闭环。

v0 要解决的核心问题是：

> 如何让个人卖家以较低的时间和试错成本，获得一份足够完整、可信、与自身条件相关的候选机会判断？

## 4. 目标用户与首发假设

### 4.1 目标用户

首发用户是一位准备进入或刚进入 Amazon FBA 的个人卖家，具备以下特征：

- 资金和时间有限，无法同时验证大量候选。
- 缺少稳定、系统化的选品研究流程。
- 会使用 Seller Central、表格和部分第三方工具，但不希望维护复杂数据系统。
- 需要中文解释，同时研究对象和原始资料可能是英文。
- 希望 Agent 主动完成信息整理，但不愿把采购和上架决策完全交给自动化系统。

### 4.2 待验证的经营假设

v0 暂按“小批量、自有品牌或轻度产品改良”设计。以下信息需要在首次使用时由用户确认：

- 经营模式：自有品牌 / 轻改良、批发、Online Arbitrage 或其他
- 可用资金和单一 SKU 的最大资金占用
- 是否已有 Amazon Professional Seller 账号
- 已订阅或可导出的第三方数据工具
- 已有供应链、擅长品类和明确禁区

经营模式变化会影响竞争判断、利润模型和推荐标准，因此不得由 Agent 静默假设。

## 5. 用户任务

### 5.1 核心 Job to Be Done

当我发现一个可能的类目、关键词或商品想法时，我希望 Agent 能主动搜集与它有关的需求、竞争、消费者问题、利润、供应链和合规信息，并结合我的资金与风险承受能力，告诉我：

- 这个机会是否值得继续投入时间和资金；
- 支持和反对它的最重要证据是什么；
- 哪些信息仍然未知；
- 如果继续，下一步最便宜、最有效的验证动作是什么。

### 5.2 次要任务

- 用户提供类目、主题、关键词或候选清单后，在限定范围内扩展并发现值得研究的细分需求。
- 比较多个候选，解释为什么某个候选更适合当前用户。
- 保存研究依据和用户决定，便于后续复盘。
- 当用户补充报价、样品或真实运营数据时，重新计算并更新建议。

在没有任何种子或范围的情况下扫描整个 Amazon 市场，属于 P1 探索能力，不是 v0 P0 的前提。

## 6. 产品原则

### 6.1 对话优先

用户通过自然语言、文件、链接和追问与同一个专业 Agent 协作。Agent 应在对话中解释当前理解、研究进度、证据缺口和建议，不要求用户先理解一套复杂的产品界面。

对话优先不等于无结构。Agent 必须把关键状态沉淀为可追溯的研究产物，避免重要信息只存在于聊天上下文中。

### 6.2 Agent 驱动、工具约束

Agent 根据目标、证据和用户反馈决定下一步研究动作，可以跳过无价值步骤、增加新的验证路径或回到之前的假设。产品不使用固定页面流程替代 Agent 判断。

确定性要求仍由工具承担，包括单位经济、费用公式、字段校验、证据引用检查和硬门槛结果。工具为 Agent 提供可靠能力，不充当顶层流程编排器。

### 6.3 信息价值优先

信息只有在满足以下至少一项时才应被优先搜集和展示：

- 可能改变“继续 / 观察 / 放弃”的决定；
- 能显著降低关键不确定性；
- 能验证或推翻一个重要假设；
- 能直接指导下一步行动。

Agent 不以网页数量、引用数量或报告长度衡量研究质量。

### 6.4 证据优先

每项关键事实必须能回溯到来源、采集时间和口径。LLM 生成的总结不是证据本身。

### 6.5 建议而非替代决策

Agent 可以提出明确倾向，但必须同时展示条件、风险、未知项和最强反对理由。采购、上架、付款和账户操作由用户确认。

### 6.6 经营约束先于热度

一个需求真实存在，不代表它适合当前用户。利润、现金占用、物流、合规和执行难度属于前置条件。

### 6.7 缺失信息也是结果

如果关键数据无法合法、可靠地取得，Agent 应明确说明缺口和影响，不得用模型猜测填补。

## 7. 核心概念

| 概念 | 定义 |
| --- | --- |
| PickScout 仓库 Agent | Codex 在当前 Git 仓库中工作时，由根目录 `AGENTS.md` 和仓库内配套资料定义的专业行为 |
| PickScout Agent 分发包 | 让其他用户在自己的工作区运行同一选品 Agent；当前通过 `adapters/codex/pickscout-agent/` 兼容 Codex，长期不绑定 Skill 机制 |
| 仓库工作台 | 当前 Git 仓库内用于调试 Agent、维护规则、运行脚本和保存研究产物的隔离空间 |
| Agent 工具 | Agent 可按需调用的搜索、浏览、文件、数据连接器或确定性脚本 |
| 研究产物 | Agent 在对话之外持久保存的卖家画像、研究简报、证据、计算、报告和决策记录 |
| 研究任务 | 围绕一个问题、细分需求或候选集合开展的一次有边界的信息搜集与分析 |
| 候选机会 | 一个客户需求 / 关键词簇 / 细分市场及其代表商品，不等同于单一 ASIN |
| 证据 | 可追溯到外部来源或用户输入、能够支持或反驳某项判断的信息 |
| 信号 | 从一个或多个证据中提取的趋势、指标或模式 |
| 事实 | 来源直接支持、无需额外推演的陈述 |
| 推断 | 基于事实和明确规则得出的解释 |
| 假设 | 尚未得到充分证据支持、需要验证的前提 |
| 建议 | 结合证据、用户约束和风险偏好提出的行动倾向 |
| Agent 建议状态 | `advance`（继续验证）、`observe`（观察等待）、`reject`（放弃）或 `insufficient`（信息不足） |
| 用户决定 | 用户独立记录的继续、观察、放弃或暂不决定，不由 Agent 建议自动填充 |
| 硬门槛 | 一旦不满足就应淘汰或暂停候选的条件 |
| 置信度 | 对证据覆盖、质量、一致性和新鲜度的综合描述，不代表成功概率 |
| 决策档案 | 研究结论、证据、用户决定、理由和后续结果的可追溯记录 |

## 8. 主要用户流程

### 8.1 建立卖家画像

首次对话中，Agent 只询问当前任务真正需要的经营条件，并逐步维护卖家画像，包括：

- 目标市场与经营模式
- 预算与现金风险边界
- 目标售价、利润和周转偏好
- 可接受的尺寸、重量、MOQ 和交期
- 禁止或暂不考虑的品类
- 供应链优势、已有数据源和账号权限

用户可以随时用自然语言补充或修改条件，不要求先完成固定表单。Agent 应复述关键约束供用户确认，并把它们沉淀为可编辑的卖家画像。每次研究任务保存当时使用的画像快照，避免后续修改导致历史结论失真。

### 8.2 发起研究任务

用户在 Codex 对话中可以通过以下任一方式开始：

- 输入关键词、需求描述、明确的细分类目或 Amazon URL / ASIN；
- 上传候选列表、平台导出或供应商报价；
- 从人工准备的种子清单中选择候选。

P0 每个任务至少需要一个具体种子，例如关键词、需求描述、明确的细分类目、ASIN、URL 或候选清单。Agent 可以在研究简报限定的市场、类目和预算内扩展相关关键词与代表商品，但不承担零种子的全市场扫描。用户仅给出宽泛类目或主题时的引导式发现列为 P1。

Agent 将目标改写为结构化研究简报，并在对话中用简洁语言确认：

- 要回答的核心问题；
- 候选范围；
- 需要搜集的信息；
- 可用来源与预计限制；
- 预期产物。

用户可以直接用自然语言修改范围。信息已足够且动作可逆时，Agent 不为固定流程而强制暂停；范围存在重大歧义时才请求确认。低成本的公开信息搜集无需逐项审批；付费数据、账户授权或可能产生外部影响的动作必须单独确认。

### 8.3 搜集与整理信息

Agent 先提出当前研究计划，再按信息价值排序调用可用工具，优先解决硬门槛和高影响未知项。研究路径不是固定步骤：新证据可以使 Agent 改变关键词、补查来源、跳过低价值问题或提前建议放弃。

搜集过程中，Agent 应通过对话提供必要的进度更新，包括：

- 当前研究进度；
- 已覆盖和未覆盖的维度；
- 使用了哪些来源；
- 是否出现冲突、过期或不可访问的数据；
- 是否需要用户补充报价、尺寸、成本或账号数据。

用户可以随时追问“为什么查这个”、改变范围、补充文件、要求暂停或让 Agent 先给阶段性判断。Agent 必须保留已完成产物，并从修改后的目标继续工作。

### 8.4 形成分析

Agent 根据当前候选选择需要执行的分析，并调用确定性工具完成硬门槛、单位经济和结构校验。标准分析维度包括：

1. 需求与趋势
2. 竞争与进入壁垒
3. 消费者问题与差异化空间
4. 单位经济与现金占用
5. 供应链与履约风险
6. 合规与知识产权风险
7. 证据完整度与不确定性

### 8.5 输出建议并由用户决策

Agent 先在对话中给出可快速阅读的结论，再按需展开证据或链接完整研究产物。每次建议必须包含：

- Agent 建议状态：
  - `advance`：硬门槛通过且核心证据达到要求，建议进入下一项验证；
  - `observe`：尚无放弃理由，但当前行动价值不足，建议等待或监测；
  - `reject`：硬门槛失败或证据明显不利，建议放弃；
  - `insufficient`：关键证据缺失，暂不能形成经营建议；
- 建议成立的前提
- 最重要的支持证据
- 最重要的反对证据
- 尚未解决的未知项
- 悲观 / 基准 / 乐观情景
- 下一步低成本验证动作

用户可以继续追问、反驳假设、要求补查，或独立选择继续、观察、放弃、暂不决定。Agent 应在用户明确表达决定后记录理由、接受的风险和下一步动作，并同步更新任务决策日志和跨任务总进度；不得把自身建议自动记录为用户决定。

### 8.6 补充信息与复盘

用户后续可以补充：

- 供应商报价与样品结果
- 实际包装、物流和检测成本
- 上线后的销量、广告、退货和利润
- 放弃候选的真实原因

Agent 保留历史版本，并基于新证据重新研究和调用计算工具。自动学习或调整全局评分不属于 v0，但研究产物需支持后续校准。

## 9. 什么叫“搜集了足够的信息”

研究任务满足以下条件时，可进入“待用户审阅”状态：

1. 所有必填分析维度至少有一项可信证据，或明确标记为缺失。
2. 所有硬门槛均为“通过”或“不通过”；任何“未知”都会使 Agent 建议状态变为 `insufficient`。
3. 需求和竞争判断各自覆盖至少两种不同的信号类型，且来自至少两个相互独立的来源家族；仅有一个来源家族时不得给出 `advance`。单位经济不要求重复来源，但所有必填输入必须有来源，并完成悲观、基准和乐观情景。
4. 关键数据处于允许的新鲜度范围，过期数据已被标记且不参与关键计算。
5. 来源冲突已经解释、保留或升级给用户，而不是被静默平均。
6. 推荐所依赖的假设均已显式列出。
7. 每项信息缺口都已标记预期决策影响；只要仍有可能触发硬门槛或改变建议状态的缺口，研究就不能视为信息足够。
8. 任务有明确停止原因，且只有 `criteria_satisfied` 可以自动进入 `ready_for_review`。

如果条件未满足，Agent 应输出“信息不足的阶段性报告”，说明缺什么、为什么重要以及如何取得，而不是生成看似完整的强建议。

提前放弃例外：如果一个具有否决作用的硬门槛“不通过”已由官方、用户授权或用户确认的证据验证，Agent 可以直接给出 `reject` 并以 `criteria_satisfied` 停止。此时无需继续搜集不会改变决定的维度，但必须逐项记录 `skipped_due_to_decisive_hard_gate`，而不能伪装成已覆盖。

### 9.1 停止原因

| 停止原因 | 行为 |
| --- | --- |
| `criteria_satisfied` | 满足上述全部条件，进入 `ready_for_review` |
| `budget_exhausted` | 时间或数据成本预算耗尽，输出阶段性报告 |
| `source_unavailable` | 关键来源不可用，进入 `needs_input` 或 `blocked` |
| `user_stopped` | 保留进度和已取得证据，等待用户继续 |

达到时间或成本上限，不等于信息已经足够。

### 9.2 信号类型

- 站内需求行为
- 站外搜索兴趣
- 价格、BSR 或 Offer 历史
- 竞争结构
- 消费者反馈与退货问题
- 单位经济
- 供应链与履约
- 合规与知识产权

### 9.3 来源家族与独立性

来源家族包括：

- Amazon 官方或卖家授权数据
- 监管机构与标准组织
- 有许可的第三方结构化数据
- 用户自有经营数据
- 供应商、物流商与检测机构
- 公开行业研究
- 社区讨论与个人经验

两个页面如果使用相同的上游数据、报告或服务，则不视为相互独立。Agent 无法确认独立性时，按不独立处理。

### 9.4 信息缺口的决策影响

每项缺口必须标记为以下一种：

- `hard_gate`：可能改变硬门槛状态
- `status_change`：可能改变 Agent 建议状态
- `confidence_only`：只影响置信度说明
- `context_only`：仅补充背景

存在未解决的 `hard_gate` 或 `status_change` 缺口时，不得使用 `criteria_satisfied`。

## 10. 信息来源与证据规则

### 10.1 来源优先级

1. 平台、监管机构和标准组织的官方资料
2. 用户授权的 Seller Central / SP-API 和自有经营数据
3. 有明确使用许可的结构化第三方数据
4. 用户上传的供应商、物流、检测和报价资料
5. 可公开访问的行业、趋势和消费者资料
6. 社区讨论和个人经验

低优先级来源可以发现线索，但不能单独支持高风险经营结论。

### 10.2 v0 支持的数据入口

- 在研究简报限定范围内主动搜索和浏览可公开访问的资料
- 用户手工输入
- CSV / XLSX 等结构化文件
- PDF、网页链接及文本资料
- Amazon 官方公开工具的用户记录或合规导出
- 经用户授权的 API；实际接入可在 v0 后续迭代完成

### 10.3 明确禁止

- 把模型自身知识当作实时市场证据
- 隐瞒来源或伪造引用
- 绕过登录、验证码、访问控制或平台限制
- 未经确认调用付费数据源
- 使用不明许可的数据训练或改进模型
- 将包含用户凭据、个人信息或商业机密的原文暴露给无关第三方

### 10.4 证据质量维度

每条证据至少评估：

- 相关性：是否直接回答当前研究问题
- 权威性：来源是否有资格提供该信息
- 新鲜度：信息是否仍适用于当前市场
- 直接性：是一手数据、转述还是推测
- 完整性：样本、时间范围和计算口径是否充分
- 一致性：是否与其他独立来源相符
- 可操作性：是否可能改变决定或下一步行动

Agent 使用“高 / 中 / 低”及文字原因表达质量，不在 v0 伪造精确概率。

## 11. 分析与建议规则

### 11.1 硬门槛

v0 至少检查：

- 平台销售资格和品类限制
- 产品安全、危险品和必要认证
- 商标、专利、外观或品牌授权风险
- FBA 尺寸、重量、包装和履约限制
- 悲观情景下的单位贡献利润
- MOQ、交期与最大现金占用
- 用户明确设置的禁区

任何硬门槛为“不通过”时，Agent 建议状态必须为 `reject`。任何硬门槛为“未知”时，Agent 建议状态必须为 `insufficient`，并说明缺失信息及其取得方式。

### 11.2 单位经济

基础模型：

```text
单位贡献利润 =
  售价
  - 平台销售佣金
  - FBA 履约费
  - 入仓运输与仓储
  - 到岸采购成本
  - 广告成本
  - 退货、损耗与移除准备金
  - 税费及汇率准备金
```

所有计算字段必须显示：

- 数值与币种
- 来源或用户输入
- 使用时间和市场
- 计算公式
- 缺失值及默认假设

Agent 必须展示情景范围，不得把单点销售预测包装成确定结果。

### 11.3 推荐表达

每项建议采用以下结构：

```text
建议：
适用条件：
支持证据：
反对证据：
关键未知：
置信度及原因：
下一步动作：
```

Agent 必须避免：

- “一定会成功”“爆款”“稳赚”等确定性承诺
- 用一个总分遮蔽某项致命风险
- 把相关性描述为因果关系
- 因为没有找到负面信息就认定风险不存在

## 13. 交互形态与 Codex-native 仓库架构

### 13.1 主要交互：持续对话

v0 直接运行在 Codex 任务中。对话承担以下职责：

- 表达模糊目标并逐步澄清；
- 提供关键词、链接、ASIN、文件和经营信息；
- 查看 Agent 的计划、阶段进度和阶段性结论；
- 追问证据、挑战假设或调整范围；
- 确认付费、授权和外部影响动作；
- 接收建议并作出最终决定。

不单独开发研究首页、聊天前端或固定步骤向导。专业性来自本仓库的 Agent 规则、研究协议、领域资料、工具和研究产物，而不是一套写死的页面流程。

### 13.2 对话背后的持久化研究产物

聊天上下文本身不是唯一数据源。Agent 在私有工作区中维护：

- 卖家画像及版本；
- 研究简报和当前计划；
- 证据账本、原始引用与信息缺口；
- 单位经济输入、公式版本和情景结果；
- 阶段性报告、最终建议与用户决定。
- 每个任务的决策检查点时间线，以及跨任务候选漏斗和当前待办总览。

统一目录约定：

- `data/`：用户导入的原始或敏感数据，Git 忽略；
- `artifacts/<task-id>/`：每个研究任务的简报、证据、计算、报告和决定，Git 忽略；
- `docs/`：可复用且已脱敏的专业规则和研究协议，进入版本控制；
- `templates/`：可复用且已脱敏的研究模板，进入版本控制；
- `scripts/`：确定性计算与校验工具，进入版本控制。
- `adapters/codex/pickscout-agent/`：当前 Codex 的兼容安装入口，进入版本控制；根目录内容仍是长期事实来源。

Agent 在对话中展示摘要，并在用户需要核查、比较或复盘时链接 `artifacts/<task-id>/` 中的完整产物。v0 可使用 Markdown、JSON 或 JSONL 文件实现，不要求先建立数据库。

### 13.3 最小执行架构

```text
Codex 任务 / 对话
  → 当前 Git 仓库的根目录 AGENTS.md，或已安装的 PickScout Agent 兼容适配器
  → 仓库内领域文档、模板与研究协议
  → Codex 已有搜索、浏览、文件与协作工具
  → 确定性计算和校验脚本
  → 可选的仓库级 .codex/config.toml 与授权 MCP 数据工具
  → data/ 原始输入与 artifacts/ 私有研究产物
  → 对话中的解释、建议与用户决策
```

职责边界：

| 层 | 职责 |
| --- | --- |
| Codex | 对话、推理、任务连续性、工具选择、权限与执行 |
| 根目录 `AGENTS.md` | PickScout 身份、仓库边界、专业原则、来源策略、停止条件和安全约束 |
| `adapters/codex/pickscout-agent/` | 面向当前 Codex 的自包含兼容入口；不定义产品本体 |
| 仓库文档与模板 | Amazon FBA 规则、研究协议、证据规范、卖家画像和报告模板 |
| Deterministic Scripts | 单位经济、费用公式、结构校验和引用完整性检查 |
| 仓库级 MCP（按需） | 通过项目 `.codex/config.toml` 为本仓库提供需要授权、认证或结构化实时数据的受控工具 |
| `data/` 与 `artifacts/` | 在仓库内保存原始输入，并跨轮次恢复事实、证据、计算、建议和用户决定 |

### 13.4 v0 实现策略

P0 在仓库根目录维护一个简洁的 `AGENTS.md`，并把方法论、标准操作程序、详细研究协议、模板、脚本和研究产物保存在本仓库。Codex 从这个仓库启动时自动获得 PickScout 的专业约束；其他用户可以通过安装 `adapters/codex/pickscout-agent/` 获得当前 Codex 的自包含兼容形态。

固定外层循环由 `docs/pickscout-methodology-v1.md`、`docs/pickscout-sop-v1.md` 和 `templates/task-run-checklist.md` 提供；它们固定阶段门槛、恢复、记录和授权，不固定搜索来源与工具顺序。

不创建 `.agents/skills/` 隐式项目 Skill，也不由仓库维护流程自动安装用户级能力、插件或修改仓库外的 Codex 配置。当前兼容适配器固定维护在 `adapters/codex/pickscout-agent/`；用户通过 Agent 安装或明确授权安装。只有现有工具无法可靠完成高价值数据动作时，才在用户确认后使用仓库级 `.codex/config.toml` 增加 MCP。

v0 不使用 Codex SDK 嵌入自建应用，也不 fork LobeHub。独立前端、服务端 Agent 编排和数据库均不是验证专业 Agent 价值的前提。

## 14. 概念数据模型

以下模型描述 Agent 必须维护的信息，不要求 v0 实现后台数据库。它们可以先作为结构化文件存在于 `artifacts/<task-id>/` 中。

### 14.1 SellerProfile

- 市场与经营模式
- 资金和风险边界
- 目标利润与周转偏好
- 供应链条件
- 类目偏好与禁区
- 可用数据源
- 版本与生效时间

### 14.2 ResearchTask

- 研究种子
- 研究目标与范围
- 允许的来源边界
- 使用的卖家画像快照
- 状态
- 时间 / 数据成本预算
- 必填分析维度
- 停止条件
- 停止原因
- 当前覆盖与缺口

状态：

```text
draft
→ researching
→ needs_input | blocked
→ ready_for_review
→ decided
→ archived
```

这些状态只用于标记研究进度和恢复任务，不规定 Agent 必须按固定顺序调用哪些工具。

### 14.3 Candidate

- 需求或关键词簇
- 代表 ASIN
- 目标规格与价格带
- 当前 Agent 建议状态摘要
- 当前用户决定摘要

建议和用户决定的完整记录分别由 `Recommendation` 和 `UserDecision` 保存。

### 14.4 Evidence

- 所属任务和候选
- 关联的 Claim ID
- 信号类型
- 来源家族
- 独立性依据
- 决策影响：`hard_gate` / `status_change` / `confidence_only` / `context_only`
- 原始引用或快照引用
- 原始内容哈希
- 来源类型、发布者和 URL / 文件
- 发布时间与采集时间
- 市场、时间范围和指标口径
- 提取方法及工具 / 模型版本
- 来源使用限制
- 质量评估
- 支持 / 反对 / 中性
- 冲突组与版本

### 14.5 Claim

- 规范化陈述或指标
- 事实 / 推断 / 假设
- 所属分析维度
- 市场、时间与适用范围
- 支持和反对它的 Evidence ID
- 当前状态与版本

### 14.6 InformationGap

- 缺失字段或待回答问题
- 所属任务、候选和分析维度
- `signal_type`
- `decision_impact`
- 当前可取得性与阻塞原因
- 建议取得方式、预计成本和优先级
- 当前状态与版本

### 14.7 Calculation

- 输入值及来源
- 公式版本
- 情景
- 输出值
- 缺失值和假设

### 14.8 Recommendation

- 建议状态：`advance` / `observe` / `reject` / `insufficient`
- 适用条件
- 支持和反对证据
- 关键未知
- 置信度说明
- 下一步动作
- 报告版本

### 14.9 UserDecision

- `decision_status`：`continue` / `observe` / `drop` / `undecided`
- `reason`
- `decider`
- `decided_at`
- `based_on_report_version`
- `accepted_risks` 与未解决假设
- `disagrees_with_agent`
- `next_action` 与 `review_at`

### 14.10 DecisionCheckpoint

- 稳定 `checkpoint_id`、所属任务与候选
- 发生时间、触发原因和所处阶段
- 当时可选方案与 Agent 建议
- 用户明确决定；未决定时为 `pending`
- 依据的报告、证据、计算或对话确认
- 理由、接受风险、关键未知和下一动作
- 复盘条件、当前状态与 `supersedes`

## 15. 失败与异常行为

| 情况 | v0 行为 |
| --- | --- |
| 数据源不可访问 | 标记失败原因，继续使用其他来源；关键维度缺失时转为 `needs_input` |
| 来源互相冲突 | 同时展示，解释口径差异；无法解决时降低置信度 |
| 数据过期 | 标记为过期，不参与关键计算，并提出刷新动作 |
| 用户成本数据缺失 | 输出不完整情景，将建议状态设为 `insufficient` |
| 研究达到预算仍不完整 | 生成阶段性报告，列出最有价值的下一项信息 |
| Agent 工具调用失败 | 保留已完成证据和进度，允许从失败点重试 |
| 对话被中断或任务稍后继续 | 从持久化研究产物恢复，先说明当前状态再继续 |
| 所需工具尚未接入 | 说明能力缺口，改用用户导入或提出最小接入需求，不虚构结果 |
| 用户改变研究范围 | Agent 更新研究简报，标记受影响的旧证据和结论，不静默混用 |
| 引用无法回溯 | 相关陈述不得作为事实进入最终建议 |
| 合规或知识产权结论不确定 | 明确提示需要专业确认，不以模型判断替代 |

## 17. 成功指标

### 17.1 v0 质量指标

- 关键证据覆盖率：必填分析维度中有可信证据或明确缺口的比例
- 关键事实可追溯率：最终报告关键事实可打开原始来源的比例
- 硬门槛完整率：报告中已通过、未通过或明确未知的硬门槛比例
- 误就绪率：进入 `ready_for_review` 后，发现当时已存在但未标记、足以触发硬门槛或改变建议状态的信息缺口的比例
- 缺失信息重开率：用户因缺少决策所需信息而要求重新打开研究的比例
- 用户决策记录完整率：决定状态、理由、报告版本和接受的风险均有记录的比例
- 决策检查点可追溯率：改变后续行动的节点中，能够还原当时选项、建议、用户决定、依据和下一动作的比例
- 研究产物完整率：任务中断或跨轮次继续后，关键证据、计算和决定仍可恢复的比例
- 对话纠偏成功率：用户改变范围或纠正假设后，Agent 正确更新计划且不混用失效结论的比例

### 17.2 效率指标

只有在质量指标达到试点要求后，才用以下指标优化速度和成本：

- 决策就绪率：研究任务达到 `ready_for_review` 的比例
- 研究周期：从任务开始到待审阅报告的时间
- 单次研究的数据与模型成本

### 17.3 质量护栏

- 无来源事实率
- 过期证据参与关键计算的比例
- 事实 / 推断 / 假设混淆率
- 因关键成本缺失仍生成 `advance` 的次数

### 17.4 业务结果指标（后续校准）

- 预测利润区间与实际结果的偏差
- 被提前识别并避免的高风险候选
- 建议验证动作带来的信息增益
- 用户决定与后续真实结果之间的复盘完整率

v0 不以“Agent 推荐被用户接受的比例”作为主要指标，避免 Agent 为了迎合用户而降低反证质量。

## 18. 验收标准

使用一组有具体种子、明确范围和授权边界的真实 Amazon US FBA 研究任务进行验收，v0 至少满足：

1. 用户可以在 Codex 中用一段自然语言或一个文件 / 链接开始研究，无需进入独立界面。
2. Agent 会生成可见的研究计划，并能根据新证据或用户纠正改变计划。
3. 用户可以在研究中追问理由、改变范围、暂停并继续，已完成研究产物不会丢失。
4. 每个最终回答和完整报告都区分事实、推断、假设和建议。
5. 每项关键事实都能回溯到来源、采集时间和口径。
6. 每个硬门槛都有“通过 / 不通过 / 未知”状态。
7. 关键成本缺失时，Agent 建议状态为 `insufficient`。
8. 单位经济可使用相同输入独立复算并得到相同结果。
9. 只有停止原因为 `criteria_satisfied` 时，研究才能自动进入待审阅状态。
10. 不满足停止条件时能在对话中输出具体信息缺口，而不是伪完整报告。
11. 每份建议包含最强支持证据、最强反对证据和下一步验证动作。
12. Agent 建议与用户最终决定分别保存；用户决定同时记录所依据的报告版本、接受的风险和是否与 Agent 意见不一致。
13. 研究任务不依赖绕过平台访问控制的 Amazon 网页抓取。
14. 验收任务中，任何已知的 `hard_gate` 或 `status_change` 信息缺口都不能进入 `ready_for_review`。
15. 关闭并继续一个试点任务后，Agent 能依据研究产物说明此前进度、未完成项和当前建议。
16. 任一候选从发现到样品或放弃的路径，都能从跨任务总进度和任务决策日志还原，且未明确的用户决定显示为 `pending`。
17. 新使用者或新 Agent 能依据方法论、SOP 和任务运行清单启动或恢复任务；每项建议均能区分当前阶段、用户决定、动作授权和执行事实。

## 19. 推进顺序

### 阶段 A：Codex 对话式研究验证

先直接通过当前 Codex 对话和统一模板完成一组有边界的真实研究任务，验证：

- 哪些证据最常改变决定；
- 哪些字段难以获得；
- 哪些硬门槛确实有淘汰价值；
- 用户实际如何追问、纠正和作出决定；
- 哪些稳定约束适合写入根目录 `AGENTS.md` 或仓库文档，哪些应继续由 Agent 动态判断。

### 阶段 B：Codex-native 仓库 Agent v0

迭代根目录 `AGENTS.md`，并在当前仓库中沉淀领域参考资料、研究模板、确定性脚本和工作台产物。P0 只处理用户提供具体种子的任务，不开发独立应用，也不安装仓库外能力。

### 阶段 B.1：可分发 PickScout Agent

把已经稳定的方法论、SOP、协议、模板和确定性脚本封装为可分发的 PickScout Agent。当前 Codex 适配器位于 `adapters/codex/pickscout-agent/`，但项目身份和核心契约不依赖 Skill 机制。分发包必须自包含、可校验，并与仓库事实来源保持一致；公开前单独完成许可证、敏感信息、仓库可见性和干净安装验收。

### 阶段 C：授权数据接入

当试点证明某个授权数据源具有稳定价值时，再通过现有连接器或 MCP 依次接入 Amazon SP-API、有许可的历史数据和用户已有工具，不预先构建大量连接器。

### 阶段 D：监测与校准

增加研究刷新、候选观察、真实经营结果回填和阈值校准。

### 阶段 E：Temu 评估

只有在 Amazon 闭环得到验证，且 Temu 的销售模式、数据权限和履约规则明确后，才建立独立的 Temu 适配和评分模型。

## 20. 开放问题

以下问题不阻碍 v0 PRD 成立，但会影响后续扩展：

1. 如何为不同经营模式提供可替换的评价约束，而不把单一卖家画像写死在产品逻辑中？
2. 哪些授权数据连接器能够稳定提高决策质量，且值得成为推荐集成？
3. 如何在多语言研究中同时保留原文证据和准确、可复核的中文解释？
4. 扩展到其他 Amazon 站点或销售平台时，哪些方法可以复用，哪些规则必须独立维护？
5. 如何建立不包含个人研究数据的公开评测集与贡献流程？
